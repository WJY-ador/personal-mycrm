# 나 · 자료 목록과 상세

> 기준: 2026-11-04 구버전 `7e93eef` 관찰·코드 조사. 최신 main은 React로 전환되어 현재 화면과 차이가 있을 수 있다. 최신 화면 실측 전 개선안은 가설이다.

## 사실

기준·결정·축·커스텀·사람·출처는 각기 다른 자료를 다루지만 별도 HTML 페이지가 아니라 공통 목록·상세·연결 구조를 재사용한다. 코드는 작은 화면에서 목록과 상세를 분리한다. [공통 렌더링](https://github.com/WJY-ador/personal-mycrm/blob/7e93eef/server/app.html#L3071) · [연결 묶음](https://github.com/WJY-ador/personal-mycrm/blob/7e93eef/server/app.html#L2963) 가짜 빈 계정의 사람·출처에는 공통 빈 안내가 보였다. 자료가 많은 각 탭은 직접 확인하지 않았다.

## 판단

자료별 의미는 달라도 목록과 상세의 조작을 일관되게 유지하는 편이 학습 비용이 작다. 기준·결정은 판단의 근거, 축은 묶음, 사람은 관계, 커스텀·출처는 자료 맥락이 우선이므로 제목과 연결 내용을 동일한 문구로 평준화하지 않는다.

| 현재 | 제안 | 이유 |
|---|---|---|
| 공통 목록·상세·연결 영역이 있다 | 열린 항목, 자료 종류, 선택 상태를 제목과 텍스트로 표시한다. hover·focus·선택 표시를 구별한다. | 색상에만 의존하지 않고 현재 문맥을 알 수 있다. |
| 모바일에서 목록과 상세가 분리된다 | 뒤로 갈 때 목록의 선택·필터·스크롤이 보존되는지 실측하고, 손실되면 복원을 후보로 둔다. | 연속 검토의 맥락을 보존한다. |
| 사람·출처의 빈 문구가 공통이다 | 기존 자료 입력 경로를 확인한 뒤 종류별 한 줄 안내를 검토한다. | 빈 이유와 실제 다음 행동을 연결한다. |
| 목록 상세 전환의 체감은 미측정 | 자주 반복하는 선택은 즉시 반영하고, 패널 이동을 쓴다면 150–250ms 후보와 무동작 대안을 시험한다. | 지연을 줄이고 방향을 이해하게 한다. |
| 항목을 드래그할 사용자 목적은 아직 확인되지 않았다 | 목록 간 이동·관계 연결용 드래그는 보류한다. | 의미 있는 이동 대상과 기존 데이터 계약이 확인되지 않았다. |

## 제안

다량 자료에서 선택→상세→원문→목록 복귀를 측정한다. [Notion의 목록·상세](https://www.notion.com/help/views-filters-and-sorts)는 비교 사례다. 패널 도입은 현행 구조의 맥락 손실이 확인되고 모바일 대안이 있을 때만 검토한다.
