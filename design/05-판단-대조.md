# 판단 목록 · 원문 대조

> 기준: 2026-11-04 구버전 `7e93eef` 관찰·코드 조사. 최신 main은 React로 전환되어 현재 화면과 차이가 있을 수 있다. 최신 화면 실측 전 개선안은 가설이다.

## 사실

가짜 기록과 후보는 DB API로 만들었다. 사용자가 실제 AI 대화에서 생성한 흐름은 시험하지 않았다. 요약→검토할 판단→목록→원문 대조에서 질문·AI 문안·강조 원문과 네 결정 버튼을 확인했다. 세 후보로 다음 분기를 실제 조작했다.

| 동작 | 실측 결과 |
|---|---|
| 건너뛰기 | 다음 후보로 이동하고 미결정 상태가 유지됐다. |
| 고쳐서 남기기 | 빈 값은 필수 입력으로 막혔다. 수정해 저장하면 다음 후보로 이동했다. |
| 반영 안 함 | 다음 후보로 이동했고 원문은 보존됐다. |
| 남기기 | `저장하고 있어요…` → `확정한 판단으로 남겼어요.`가 나타나고 확정 건수가 늘었다. 마지막 후보 뒤 `아직 안 정한 문장이 없어요`와 `구조로 돌아가기`가 보였다. |

완료→구조→확정 판단 필터를 통해 확정 문장을 다시 찾았다. 확정 카드 클릭은 판단 상세가 아니라 연결 원문 모달을 연다. 한 장짜리 대조에서도 확정 결과를 확인했다. 별도 `나` 상세에는 미결 후보를 즉시 남기는 경로가 코드에 있다. [상세 동작](https://github.com/WJY-ador/personal-mycrm/blob/7e93eef/server/app.html#L2592)

원문 로드와 인용 일치 전 결정 버튼을 잠그고 저장 중에는 결정·편집·이동을 잠근다. 응답 시간 초과는 상태를 다시 조회하고, revision 충돌 시 편집 중인 문장이 저장되지 않았음을 알린다. 이는 [화면 코드](https://github.com/WJY-ador/personal-mycrm/blob/7e93eef/server/app.html#L2202)의 정적 확인이다. DB는 근거 적격성을 재검사하고 반복 요청을 멱등 처리한다. [DB 처리](https://github.com/WJY-ador/personal-mycrm/blob/7e93eef/server/db.py#L1327) 확정 상세에서 되돌리기 버튼은 찾지 못했으나 UI 전체에 없다고 단정하지 않는다.

390px 모바일 에뮬레이션에서 대조 화면의 세로 배치와 가로 넘침 없음, 미결 카드의 Enter 열기를 확인했다. 실제 터치·스크린리더·전체 키 순서는 미확인이다. 목록의 AI 관련 세 표시가 중복 부담이 되는지는 사용자 검증 전 가설이다.

## 판단

AI 문안과 원문을 한 번에 비교하고 확정 전 상태를 표시하는 것은 핵심 신뢰 장치다. 확정 후 현재 위치와 결과를 확인하는 연결을 먼저 점검한다. 결정 행위를 멋진 효과로 대체하지 않는다.

| 현재 | 제안 | 이유 |
|---|---|---|
| 네 버튼의 분기와 저장·완료를 실측했다 | 기본 동작은 명확히 강조하고 다른 세 선택은 의미를 구분한다. press 100–150ms는 실측치가 아닌 초기 제안 범위다. 반복 이동은 즉시 반응하고 움직임 줄이기를 따른다. | 중요한 판단의 선택과 저장 상태를 오인하지 않는다. |
| 완료→구조→확정 필터로 확정 문장을 다시 찾았다 | 완료 화면에서 기존 확정 필터로 가는 링크 또는 개별 판단 상세 진입 가능성을 확인한다. `확정한 판단 보기`처럼 무엇이 열리는지 명시하고, 건너뛰기·반영 안 함만 한 경우에는 확정 결과로 유도하지 않는다. | 결과 확인의 우회 경로를 줄이되 다른 분기의 의미를 섞지 않는다. |
| 확정 카드 클릭은 연결 원문 모달을 열었다 | 상태별 카드의 동작이 `대조하기`인지 `원문 보기`인지 텍스트나 접근성 이름으로 예측 가능한지 시험한다. | 카드가 무엇을 열지 미리 알 수 있다. |
| 원문을 강조하고 AI 출처를 표시한다 | 원문·AI 후보·확정 판단의 색과 텍스트 구분을 유지한다. 중복 AI 문구는 의미가 같은지 확인한 후 정리한다. | 신뢰 근거를 유지하면서 반복 부담을 줄인다. |
| 목록→상세 이동을 확인했다 | 이동 시 선택·필터·스크롤 복귀를 검증한다. 빈번한 다음 후보 전환은 즉시, 패널 모션은 필요할 때만 짧게 적용한다. | 연속 검토에 지연을 더하지 않는다. |
| 드래그 확정은 없다 | 확정·제외·수정을 드래그로 대체하지 않는다. | 실수 복구와 키보드 접근을 명시적 버튼으로 보장한다. |

## 제안

| 순서 | 현재 가능한 경로 | 검토할 변경 | 검증 방법 |
|---|---|---|---|
| 1 | 후보 카드→원문 대조→결정. 나 상세에도 즉시 남기기 경로가 있다. | 두 경로의 진입 조건과 열리는 화면을 명확히 표시한다. | 원문 불일치·불러오기 실패에서 결정 잠금이 유지되는지 확인한다. |
| 2 | 마지막 후보 처리 후 구조로 돌아가 확정 필터를 연다. | 기존 확정 필터 링크 또는 개별 상세 진입을 검토한다. 새 API를 전제하지 않는다. | 확정·수정 확정·제외·건너뛰기 조합에서 목적지와 라벨을 시험한다. |
| 3 | 저장 중 잠금, 시간 초과 재조회, 충돌 안내가 코드에 있다. | focus·처리 중·오류·편집 문장 보존을 사용자 관점에서 확인한다. | 네트워크 오류·다른 탭 충돌·키보드 순서·모바일과 스크린리더를 시험한다. |
| 4 | 확정 후 되돌리기 버튼은 확인한 상세에서 찾지 못했다. | 취소·수정 행동을 추가하기 전 UI 전체와 기존 복원 계약을 조사한다. | 실제 복원 가능 범위와 근거·상태 보존을 확인한다. |
